## 1. Философия правдоподобия (научная опора)

Датасет должен воспроизводить эффекты, которые в реальных данных документированы
исследованиями. Опорные факты:

- **Реальные ряды снятий в банкоматах** (соревнование NN5, 2008): 2 года
  **ежедневных** снятий по 111 банкоматам Англии. Ряды демонстрируют
  **множественную сезонность, тренды, структурные сдвиги, нули и пропуски**, и у
  всех — **недельная сезонность**. Это наш эталон «как выглядит правда». Мы обязаны
  воспроизвести те же качественные свойства. [NN5 / Monash archive]
- **Кластеризуемость банкоматов.** Venkatesh et al. кластеризовали банкоматы по
  профилю снятий по дням недели (Sequence Alignment Method) и улучшили прогноз —
  прямое подтверждение, что сегментация по поведению осмысленна. [Venkatesh et al.]
- **Точечные процессы.** Поток транзакций — **неоднородный пуассоновский процесс
  (NHPP)** с интенсивностью λ(t). Но у чистого NHPP дисперсия равна среднему, а
  реальные потоки **переразбросаны** (overdispersion). Решение из литературы —
  **смешанный/Cox-процесс** (случайная интенсивность) либо отрицательное
  биномиальное распределение счётчиков. Мы используем NB-счётчики + суточный
  джиттер (эквивалент Cox). [NHPP, Cox processes]
- **Прецедент синтетики.** PaySim — агентная генерация ~6.3 млн мобильных
  транзакций за 744 часовых шага с **инъекцией аномалий** (доля фрода ~0.13%).
  Наш подход и доля аномалий калибруются по этому прецеденту. [PaySim]
- **Структурные сдвиги реальны.** Прогноз спроса ATM «до и во время COVID»
  показал резкую смену режима — обоснование нашего concept drift в году 2.
  [ATM cash demand COVID]

Полная библиография — §10.

## 2. Парсинг реальных данных (заменяет синтетические заглушки)

Цель — заземлить географию, погоду и курс на **реальные ряды**. Всё складываем в
`external/` (в `.gitignore`), кэшируем на диск, чтобы не дёргать источники повторно.
Транзакции остаются **синтетическими** — мы берём из реальности только контекст
(координаты, погода, курс), а не чьи-либо реальные операции.

### 2.1. Локации и координаты банкоматов

Нужна правдоподобная геопривязка ~120 точек в Бишкеке. Источники по приоритету:

1. **OpenStreetMap / Overpass API** — банкоматы тегированы `amenity=atm`, часто с
   `operator`/`brand`. Запрос по площади Бишкека:
   ```
   [out:json][timeout:60];
   area["name"="Бишкек"]->.a;
   node["amenity"="atm"](area.a);
   out body;
   ```
   Фильтровать по `operator~"MBank|Кыргызстан"` где есть; остальные точки — как
   общий пул банкоматов (для реалистичной плотности). Лицензия ODbL → указать
   атрибуцию. Endpoint: `https://overpass-api.de/api/interpreter`.
2. **Карта банкоматов MBank** (`mbank.kg/maps`) — за интерактивной картой обычно
   стоит JSON-endpoint со списком точек (адрес, lat/lon, режим). Проверить
   Network-запросы страницы; если есть — распарсить.
3. **2GIS** — филиалы/банкоматы MBank; есть публичное API (нужна регистрация
   ключа) либо разбор выдачи. Использовать как дополнение/сверку.

Что сохраняем в `external/atm_locations.parquet`: `source_id, lat, lon, address,
district_hint, placement_hint, is_24_7_hint`. Далее `atms.py` использует эти
точки как **скелет размещения** (привязка к нашим зонам по ближайшему центру),
сохраняя синтетические поведенческие атрибуты.

> **Этика/легальность.** Берём только публичные геоданные, уважаем `robots.txt` и
> ToS, разумные задержки между запросами, кэш. Координаты — лишь географический
> каркас; никаких персональных/транзакционных реальных данных не парсим.

### 2.2. Историческая погода (Open-Meteo Historical Weather API)

Бесплатно, без ключа, реанализ ERA5, почасовое и суточное разрешение, JSON/CSV,
лицензия CC BY 4.0 (атрибуция обязательна). Координаты Бишкека ~ (42.87, 74.59).

**Суточный запрос** (для `dim_calendar`):
```
https://archive-api.open-meteo.com/v1/archive
  ?latitude=42.87&longitude=74.59
  &start_date=2024-01-01&end_date=2025-12-31
  &daily=temperature_2m_mean,temperature_2m_max,temperature_2m_min,
         precipitation_sum,snowfall_sum,windspeed_10m_max,weathercode
  &timezone=Asia/Bishkek
```
**Почасовой запрос** (опционально, для внутрисуточных погодных эффектов):
`&hourly=temperature_2m,precipitation,snowfall`.

Сохраняем `external/weather_daily.parquet` и (опц.) `weather_hourly.parquet`.
`calendar.py` подменяет синтетические `temp_avg`/`precip_mm` на реальные, добавляет
`snowfall_mm`, `wind_max`, `weathercode`. Реальные снегопады/морозы дают честные
провалы уличных банкоматов.

### 2.3. Курс USD/KGS (исторический ряд)

Источник — **Национальный банк КР (НБКР)**: публикует официальные ежедневные
курсы, есть архив/выгрузка (XML/страница по датам). Спарсить дневной ряд USD/KGS
за 2024–2025 → `external/fx_usd_kgs.parquet` (`date, rate`). `calendar.py`
подменяет синтетический `usd_kgs_rate`, пересчитывает `fx_change_pct` и помечает
`fx_shock` по реальной волатильности. Опционально добавить RUB/KGS (ремитансы из
РФ) и EUR/KGS.

### 2.4. Календарь праздников (уточнение)

Уже реализован по официальным данным КР. Дополнить: реальные **переносы выходных**
(постановления Кабмина по годам) и уточнённые даты **Орозо/Курман айт** —
подтянуть из официального производственного календаря КР.

### 2.5. Модуль парсинга

Новый пакет `parsers/`:
```
parsers/
  osm_atms.py       # Overpass → external/atm_locations.parquet
  mbank_map.py      # mbank.kg/maps JSON (если доступен)
  weather.py        # Open-Meteo archive → weather_daily/hourly.parquet
  fx.py             # НБКР → fx_usd_kgs.parquet
  run_all.py        # оркестратор с кэшем и ретраями
```
Требования: кэш на диск, вежливые задержки, ретраи с backoff, оффлайн-режим
(если сеть недоступна — падать в синтетические заглушки, датасет всё равно
генерируется). Все внешние данные — в `external/` (gitignore).

## 3. Порождающая модель потока снятий

### 3.1. Базовая конструкция: NHPP + перерасход дисперсии

Для каждого банкомата `a` и часа `h` даты `d` число снятий моделируем как
счётчик из **отрицательного биномиального** распределения со средним
`λ(a, d, h)` и параметром дисперсии `r` (перерасход над Пуассоном — как требует
эмпирика). Эквивалентно Cox-процессу: дневной множитель `ε` (лог-нормальный)
играет роль случайной интенсивности.

```
N(a, d, h) ~ NegBinomial(mean = λ(a, d, h), dispersion = r_type)
```

### 3.2. Мультипликативная интенсивность

```
λ(a, d, h) = λ0(a)                      # базовая интенсивность банкомата (dim_atm)
           · H[type(a), h]              # суточный профиль типа (Σ_h = 24, норм.)
           · D[type(a), dow(d)]         # коэффициент дня недели (среднее = 1)
           · Pay(d, type(a))            # зарплатные дни
           · Pension(d, type(a))        # пенсии (с 10 числа)
           · Holiday(d, type(a))        # праздники и предпраздничные пики
           · Ramadan(d, h, type(a))     # пост: день ↓, вечер ↑
           · Season(d) · Trend(d, a)    # сезон + рост/цифровизация год-2
           · Weather(d, type(a))        # температура/осадки/снег
           · FX(d, type(a))             # скачок курса → набег в обменники (нал)
           · ε(a, d)                    # лог-нормальный дневной шум (Cox)
```

Все множители безразмерны, ≈1 в нейтральных условиях. Мультипликативность даёт
правостороннюю асимметрию объёмов (как в реальности) и не уводит λ в минус.

### 3.3. Суточные профили `H[type, h]` (24 значения на тип)

Задаём как сумму гауссовых «горбов» по часам, нормируем. Формы по типам:

- **transport_market:** два горба — утро (08–11) и вечер (16–18), рынок работает
  рано; ненулевой фон днём.
- **office_business:** пики 09–10, обед 13, после работы 18; ночью ~0.
- **residential:** один вечерний горб 18–21; днём умеренно.
- **shopping_mall:** плато 14–21 с пиком к вечеру; открывается к полудню.
- **tourist_center:** широкое плато 11–19, ровное.
- **pension_social:** дневной горб 09–13; вечером мало.
- **highway_gas:** почти ровный фон 08–20, слабые пики; ночью ненулевой (24/7).

### 3.4. Недельные коэффициенты `D[type, dow]` (7 значений, среднее = 1)

- office_business: будни ≫ выходные (сб/вс ~0.2–0.3).
- shopping_mall, residential: выходные > будни.
- transport_market: будни ≈ выходные (рынок «не спит»).
- pension_social: будни > выходные, привязка к дате важнее дня недели.
- highway_gas, tourist_center: слабая недельная модуляция.

### 3.5. Календарные бусты

- **Pay** (`is_payday`): office_business ×1.8–2.5 в окна 10–14 и 25–27; residential
  ×1.3; остальные слабее. Пик в первый день окна, спад к концу.
- **Pension** (`is_pension_day`): pension_social ×2.5–3.5 в окно 10–14; residential
  ×1.2 (семьи пенсионеров). Реальная привязка — выплата с 10 числа.
- **Holiday:** предпраздничные дни (`is_pre_holiday`) — резкий пик снятий
  (закупки): ×1.5–2.5, сильнее для mall/market перед НГ/Ноорузом/Курман айтом.
  В сам праздник office ≈0, mall/market могут расти.
- **Ramadan:** днём активность ↓ (×0.8), вечером после ифтара ↑ (×1.2); перед
  Орозо айт — всплеск.

### 3.6. Сезон и погода

- **Season:** tourist_center летом ↑ (×1.3–1.5), зимой ↓. Общий лёгкий годовой ход.
- **Weather:** сильный мороз/снегопад/ливень снижают поток уличных
  (`transport_market`, `residential`, `highway_gas`): множитель падает при
  `temp < −10` или большом `snowfall`/`precip`. Indoor/mall почти не затронуты.
  Формула — гладкая функция от `temp_avg`, `precip_mm`, `snowfall_mm`.

### 3.7. FX-шок → спрос на наличность

Резкий скачок курса USD/KGS (`fx_shock` или большой `|fx_change_pct|`) вызывает
кратковременный **набег за наличкой** (обменники работают только с налом):
буст ×1.3–2.0 на 1–3 дня, сильнее у market/tourist/business. Это фактор `FX`.
Механика набега — общий каталог аномалий §7.3.

### 3.8. Тренд и цифровизация (год-2, concept drift)

`Trend(d, a)` — произведение:
- **логистического роста** базы карт/операций (плавный ↑ к году 2);
- **ступеней** ввода новых банкоматов (`install_date`): точка «включается»;
- **эффекта замещения**: у клиентов с `preferred_channel=mobile` доля снятий
  снижается в году 2 (QR/безнал), что частично гасит рост.

Чистый эффект — рост объёма ~+10–15% в году 2 при **смене структуры** (выше доля
QR/NFC `entry_mode`, крупнее средний чек из-за инфляции). Подробности §4.3, §4.4.

## 4. Модель клиента и катчмента

### 4.1. Привязка транзакции к клиенту (гравитационная модель)

Кто снимает на банкомате `a` — определяется **катчментом** (моделью притяжения,
аналог модели Хаффа для ритейла): вероятность выбора клиентом `c` банкомата `a`
∝ (привлекательность `a`) / (расстояние `c`–`a`)^β, с учётом соответствия
демографии клиента типу банкомата (пенсионер → pension_social; бизнес → market;
affluent → mall). Практически:

- Для каждого банкомата заранее строим **пул вероятных клиентов** (взвешенный по
  `home_district`, демографии, сегменту).
- В момент транзакции сэмплируем клиента из пула. Ограниченность пула даёт
  **повторных клиентов** → возможность RFM, частоты, лояльности.
- Доля off-us (чужие банки/туристы) — синтетический пул без `customer_id`,
  выше у market/tourist.

### 4.2. Сумма снятия

`amount ~ LogNormal(μ[type, income_band], σ[type])`, затем:
- **округление к номиналам** банкомата (люди снимают «круглые» суммы — важная
  деталь; см. также закон Бенфорда для проверки правдоподобия старших цифр);
- **обрезка** сверху `txn_limit` (20 000–25 000) и дневным лимитом на карту;
- **инфляция года-2**: μ ×(1+~0.08).
- `dispensed_amount ≤ requested_amount` (при нехватке номиналов — недовыдача).

### 4.3. Тип операции и канал

- `txn_type`: в основном `withdrawal`/`fast_cash`; доли `balance_inquiry`,
  `mini_statement`, `transfer`, редкие `deposit` на ресайклерах.
- `entry_mode`: `chip` доминирует в году 1; доля `contactless`/`qr` растёт в году 2
  (только на банкоматах с `supports_nfc`/`supports_qr`) — часть concept drift.
- `card_scheme`: из `dim_card` для on-us; для off-us — свой микс (у туристов выше
  Visa/Mastercard/UnionPay).

### 4.4. Повторное поведение (RFM)

Часть клиентов — «частотники» (зарплатники снимают в дни выплат, пенсионеры
10–14 числа), часть — эпизодические. Пул карт ограничен → распределение частоты по
картам имеет «толстый хвост» (реалистично). Это заранее закладывает возможность
клиентской сегментации и RFM-анализа поверх готовых данных.

## 5. Развёртка до секунды и поля процессинга

- Внутри часа моменты снятий — пуассоновский процесс: равномерный джиттер по
  секундам (при желании — микропрофиль). Каждой транзакции: `timestamp` (сек),
  `session_duration_s`, `network_latency_ms`, `pin_attempts`.
- Поля ISO-8583-стиля: `rrn`, `stan`, `mcc` (6011), `auth_code`, `response_code`,
  `entry_mode` — по спецификации схемы (`design.md` §3.1).
- **Коды ответа** (`response_code`): ~92–95% `00`; остальное — `51` (нехватка
  средств), `55` (неверный PIN, иногда изъятие `41/43`), `91/92` (эмитент/сеть —
  коррелируют с `fact_atm_status`), `99` (нет наличных — растёт перед инкассацией),
  `94` (дубль). Доли off-us и распределение кодов зависят от типа/состояния ATM.

## 6. Инкассации и остаток наличности (cash management)

Симулируем баланс наличных каждого банкомата как убывающий по снятиям и
пополняемый инкассацией:

- Остаток `cash_level` уменьшается на `dispensed_amount` каждой операции.
- **Политика пополнения**: порог (например, при <15% ёмкости) или расписание по
  `service_route_id`; событие пишется в `fact_cash_ops` (сколько и каких номиналов
  загружено, `balance_before/after`).
- Если остаток дошёл до нуля до инкассации → **out_of_cash**: рост `99`, обрыв
  снятий, запись в `fact_atm_status`. Это одновременно реалистичный операционный
  процесс и источник аномалий (§7.1). Литература по оптимизации остатков ATM
  (Simutis et al.; NN5-задача) — обоснование механики.

## 7. Каталог аномалий (для будущих студенческих задач)

Аномалии **закладываются генератором и логируются в ground truth** (`labels/`),
чтобы позже сформулировать задачи «найди аномалию» и объективно оценить студента.
Общая доля аномальных событий калибруется скромно (ориентир PaySim ~0.1–1%).
Для каждой — механизм, параметры, что и каким методом ищется.

| # | Аномалия | Механизм генерации | Параметры | Ground truth | Что ищет студент (метод) |
|---|----------|--------------------|-----------|--------------|--------------------------|
| 7.1 | **Опустошение (out_of_cash)** | остаток дошёл до 0 до инкассации | порог, частота инкассаций | `labels/cash_events` | провал снятий + всплеск `99` (правила, DBSCAN по дню-ATM) |
| 7.2 | **Сбой/нет связи** | серия `91/92/96`, простой | длительность, частота | `fact_atm_status` | флэтлайн/дыры (детекция простоев, isolation) |
| 7.3 | **Ажиотаж / bank run** | FX-шок или слух → буст по сети 1–3 дня | триггер-дата, амплитуда | `labels/events` | коллективный выброс (сетевой день-аномалия) |
| 7.4 | **Новый банкомат (cold start)** | `install_date` в периоде → короткая история | доля новых (12%) | `dim_atm.install_date` | усечённая история (устойчивость моделей, пропуски) |
| 7.5 | **Праздничные пики** | предпраздничный буст | множители по праздникам | `dim_calendar` | сезонные выбросы (декомпозиция, не путать с аномалией) |
| 7.6 | **Concept drift (год-2)** | тренд + смена структуры каналов/чека | скорость дрейфа | `labels/drift_spec` | деградация модели года-1 на годе-2 (мониторинг дрейфа) |
| 7.7 | **Скимминг/фрод-паттерн** | серия off-us ночью на одном ATM, нетипичные суммы | доля ~0.1%, окна | `labels/fraud` | точечные выбросы (IsolationForest, правила, супервайзд) |
| 7.8 | **«Зависший» терминал** | флэтлайн: одинаковые/нулевые значения | длительность | `fact_atm_status` | константный участок (правила/дисперсия) |
| 7.9 | **Смена паттерна зоны** | реновация/переезд рынка → сдвиг профиля ATM | дата сдвига, редко | `labels/regime_shift` | change-point detection |
| 7.10 | **Гео-невозможность (опц.)** | одна карта на далёких ATM за минуты | доля крошечная | `labels/fraud` | velocity-правила, фрод-фичи |

**Хранилище ground truth:** каталог `labels/` (gitignore), Parquet-файлы с
метками событий (id, atm_id, интервал, тип, параметры). Плюс `meta/generation_*`
со скрытыми параметрами (λ0, коэффициенты) для полной воспроизводимости и
«ответов преподавателя».

> Принцип: аномалии **структурированы и параметризованы**, а не «просто шум» —
> чтобы у каждой задачи был проверяемый правильный ответ.

## 8. Технические требования

- **Стек:** Python 3.12, `numpy` (векторизация), `pandas`, `pyarrow`.
- **Воспроизводимость:** единый `seed`, независимые RNG-потоки (`spawn`) на модуль;
  все параметры — в `config.yaml`; скрытые параметры и метки — в `meta/`, `labels/`.
- **Производительность:** ~12 млн посекундных транзакций — генерация за минуты;
  батч-развёртка из почасовых счётчиков, без питон-циклов по транзакциям.
- **Хранение:** `fact_transactions` — Parquet, партиции `year=YYYY/month=MM/`.
  Справочники — Parquet (+ CSV-зеркало мелких). Внешние данные — `external/`.
- **Оффлайн-устойчивость:** при недоступности парсеров — падение в синтетические
  заглушки; датасет генерируется всегда.
- **Тесты:** unit-тесты на суммы долей (типы, коды ответа), диапазоны, отсутствие
  отрицательных λ; smoke-тест генерации на 3 днях.

## 9. Критерии приёмки (правдоподобие)

Датасет считается принятым, если EDA-ноутбук `00_eda_sanity.ipynb` подтверждает:

1. **Недельная сезонность** у всех банкоматов (как в NN5).
2. **Суточные профили** различаются по типам (рынок ≠ офис ≠ спальный).
3. **Зарплатные/пенсионные пики** в верные даты месяца.
4. **Праздничные всплески** перед НГ/Ноорузом/Курман айтом.
5. **Погодные провалы** уличных ATM в морозы/снегопад (по реальной погоде).
6. **FX-шоки** дают набеги за наличкой.
7. **Год-2 ≠ год-1:** объём, средний чек, доля QR/NFC; виден дрейф.
8. **Коды ответа** реалистичны (~92–95% `00`); `99` растёт перед инкассацией.
9. **Толстый хвост** частоты снятий по картам (повторные клиенты).
10. **Кластеры честно перекрываются** (типы residential/pension_social близки) —
    KMeans ошибается, GMM/иерархия помогают.
11. **Аномалии из §7 различимы** и присутствуют в `labels/`.
12. **Закон Бенфорда** для сумм выполняется приблизительно (проверка реализма).

Дополнительно — сверка агрегатов с публичной статистикой (доля кэша ~70%,
средний чек, лимиты 20–25 тыс KGS), чтобы масштабы совпадали с реальностью КР.

## 11. План работ (этапы и артефакты)

1. **Парсеры** (`parsers/`) → `external/`: погода (Open-Meteo), курс (НБКР),
   локации (OSM/MBank). Подмена заглушек в `calendar.py`/`atms.py`.
2. **`intensity.py`** — профили `H`, `D`, все факторы λ, тесты диапазонов.
3. **`transactions.py`** — NB-счётчики → развёртка до секунды → поля процессинга →
   Parquet-партиции.
4. **`cash_ops.py`** — баланс наличности, инкассации, `out_of_cash`, статусы.
5. **`anomalies.py`** — инъекция аномалий §7 + запись `labels/`.
6. **`00_eda_sanity.ipynb`** — проверка критериев приёмки §9.
7. **Тюнинг** параметров до прохождения приёмки; фиксация версии датасета.
